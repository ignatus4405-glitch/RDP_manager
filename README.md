[Changelog](CHANGELOG.md)

Централизованное хранилище и лаунчер подключений **RDP / AnyDesk / RustDesk** с встроенной документацией.
Состоит из двух частей:

| Часть | Что это | Где запускается |
|-------|---------|-----------------|
| **Сервер** (`server/`) | REST API + SQLite + веб-панель администратора; в Windows — настоящая служба с отдельным GUI-управлением и треем, в Linux — systemd | Сервер в локальной сети (Windows, Linux) |
| **Десктоп-клиент** (`client/`) | Программа сотрудника: вход под своей учётной записью, поиск по базе, запуск RDP / AnyDesk / RustDesk в один клик, чтение документации | Компьютеры сотрудников и администраторов |

## Структура репозитория

```
RDP_manager/
├── server/                 # Серверная часть (Node.js + Express + SQLite)
│   ├── src/
│   │   ├── index.js        # Точка входа: HTTP-сервер, раздача панели и веб-клиента, RDP-шлюз
│   │   ├── api.js          # REST API: auth, пользователи, подключения, документы, статистика
│   │   ├── db.js           # SQLite (node:sqlite), схема БД, scrypt-хеши, первичный admin
│   │   ├── auth.js         # HMAC-JWT токены, middleware авторизации и ролей
│   │   └── rdp-gateway.js  # RDCleanPath-шлюз (WebSocket /ws/rdp → TCP/TLS → RDP), JWT + allowlist по БД
│   ├── web/index.html      # Встроенная веб-панель администратора (создание админов и пр.)
│   ├── scripts/build-sea.js  # Однофайловый SEA-бинарник сервера (esbuild + postject)
│   ├── installer/          # WinSW-конфигурация Windows-службы; Linux install.sh + systemd-юнит
│   └── data/               # Создаётся при первом запуске: rdp-manager.db, secret.key (в .gitignore)
├── client/                 # Десктоп-клиент (Electron)
│   ├── main.js             # Главный процесс: окно + mstsc / внешний запуск AnyDesk / RustDesk
│   ├── preload.js          # Безопасный IPC-мост (contextIsolation)
│   ├── renderer/           # UI: index.html, styles.css, app.js, md.js (Markdown)
│   │   ├── ironrdp-entry.mjs # Вход ironrdp-бандла (IronRDP WASM + wasm как data:URL)
│   │   └── vendor/         # Собирается scripts/build-ironrdp.js (в .gitignore)
│   ├── scripts/build-ironrdp.js  # Сборка vendor/ironrdp/bundle.js (esbuild, IIFE)
│   └── assets/icon.png     # Иконка приложения
└── package.json            # npm workspaces: server + client
```

## Автосборка и автообновление (GitHub Actions)

Три workflow (`.github/workflows/`):

| Workflow | Когда запускается | Что делает |
|----------|-------------------|------------|
| **CI** (`ci.yml`) | каждый push (любая ветка) и PR | `node --check` всех JS, смоук-тесты сервера, проверка electron-builder |
| **Build** (`build.yml`) | любой push (ветки и теги), PR в `main`, вручную | единый компонентный установщик (**Windows NSIS: клиент / Windows-служба / оба**), клиент (**Linux AppImage**) и сервер (**Linux tar.gz + systemd**); генерация `latest(-linux).yml`; на теге `v*` — публикация в GitHub Release |
| **Release Please** (`release.yml`) | push в `main` | workflow оставлен в репозитории, но `GITHUB_TOKEN` не имеет прав создать PR; версию и CHANGELOG выпускают вручную через release PR |

**Релизный процесс (вручную):**
1. После слияния изменений подготовьте отдельный PR: синхронно обновите версии root/client/server, `package-lock.json`, release manifest и `CHANGELOG.md`.
2. Дождитесь зелёных CI/Build-проверок и влейте release PR.
3. Вручную создайте и отправьте тег `vX.Y.Z` на merge-коммит релизного PR; тег запускает Build.
4. Проверьте публикацию командой `gh release view vX.Y.Z`: Windows installer, Linux AppImage, Linux server tar.gz и `latest*.yml` должны быть в Release.
5. Установленные клиенты проверяют/загружают обновления; Server Manager открывает страницу релиза, откуда пользователь запускает единый установщик с нужным компонентом.

Текущие версии пакетов: `1.4.10`. Подробности — `CONTRIBUTING.md`, `AGENTS.md`, `CHANGELOG.md`.

## Требования

- **Node.js ≥ 22.5** нужен только для запуска сервера из исходников; готовый SEA-сервер уже содержит Node.js и `node:sqlite`.
- На **клиентском** компьютере:
  - Windows: `mstsc.exe` (для внешнего RDP) и установленный AnyDesk для подключений AnyDesk;
  - Linux: `xfreerdp3`/`xfreerdp` или `remmina` для внешнего RDP и `anydesk` в `PATH` либо системный обработчик `anydesk:`;
  - RustDesk в десктоп-клиенте экспериментально встроен и требует доступа к WebSocket-портам собственного RustDesk-сервера и его публичного ключа; см. `docs/rustdesk-integration.md`.
- Сеть: клиентские ПК должны видеть порт сервера (по умолчанию **8720**, TCP).

## Установка из готовых установщиков (рекомендуется)

Windows-клиент и Windows-сервер входят **в один установщик**; Linux-пакеты остаются отдельными:

| Файл | Что | Куда ставится |
|------|-----|----------------|
| `RDPManager-Setup-<версия>.exe` | единый Windows NSIS-установщик: выбор «Клиент» / «Серверная служба + GUI» / «Оба» | `C:\Program Files\RDP Manager` (папка установки выбирается) |
| `RDPManager-<версия>.AppImage` | десктоп-клиент (Linux) | портативно |
| `RDPManager-Server-<версия>-linux-x64.tar.gz` | сервер (Linux) | `/opt/rdp-manager-server` |

**Windows-сервер**: запустите `RDPManager-Setup-<версия>.exe` от имени администратора и выберите «Серверная служба + графическое управление» (или «Клиент и сервер»). Установщик регистрирует настоящую службу `RDPManagerServer` с автоматическим запуском и восстановлением после сбоя, открывает TCP 8720 в брандмауэре и запускает службу. База и секрет хранятся в `%ProgramData%\RDP Manager Server\data`; логи — в `%ProgramData%\RDP Manager Server\logs\server.log` (ротация, окно GUI показывает последние записи). При переходе со старого отдельного Windows-установщика его задача удаляется, а база и ключ копируются в `%ProgramData%`; если выбран «Только десктоп-клиент», старая служба снимается, данные сохраняются для возможной последующей установки сервера.

Из меню «Пуск» откройте **«Управление сервером»**: окно показывает состояние, позволяет запускать/останавливать/перезапускать службу (Windows запросит UAC), открывать веб-панель, читать логи и проверять обновления. При входе пользователя в Windows менеджер запускается свёрнутым в трей; закрытие окна также скрывает его в трей. Из меню трея можно вернуться в GUI, открыть панель и управлять службой. Веб-панель: `http://<IP-сервера>:8720/`.

**Сервер на Linux**:
```bash
tar -xzf RDPManager-Server-<версия>-linux-x64.tar.gz
cd rdp-manager-server
sudo bash install.sh
```
Ставит в `/opt/rdp-manager-server`, запускает systemd-юнит `rdp-manager-server` (пользователь `rdp-manager`). Логи: `journalctl -u rdp-manager-server -f`. Удаление: `sudo bash uninstall.sh` (БД сохраняется), полный снос: `sudo bash uninstall.sh --purge`.

**Дальше на каждом клиентском ПК**: запустите единый `RDPManager-Setup-<версия>.exe` и выберите «Только десктоп-клиент» (или установите AppImage на Linux), затем укажите адрес сервера, логин и пароль.

## Быстрый старт: сервер (из исходников)

```bash
npm install          # установить зависимости (server + client)
npm run server       # запустить сервер
npm run server-manager # dev-GUI службы (управление службой доступно в Windows)
```

При первом запуске создаётся база (`server/data/rdp-manager.db`) и учётная запись администратора:

```
логин:  admin
пароль: admin123   ← смена обязательна при первом входе (клиент потребует это явно)
```

После запуска доступно:

- **API:** `http://<IP-сервера>:8720/api`
- **Веб-панель администратора:** `http://<IP-сервера>:8720/` — состояние сервера и управление учётными записями (создание админов и сотрудников, сброс паролей, отключение, удаление)
- **Веб-режим клиента:** `http://<IP-сервера>:8720/app/` — тот же клиент в браузере (удобно проверить, что сервер работает; запуск подключений и документов из браузера ограничен — полный режим только в десктоп-клиенте)

## Быстрый старт: десктоп-клиент

```bash
npm run client       # dev-запуск Electron-окна
```

В окне входа указывается **адрес сервера** (например `http://192.168.0.10:8720`), логин и пароль. Адрес запоминается на этом ПК.

### Сборка установщика

```bash
npm run dist         # Windows: единый компонентный NSIS; Linux: AppImage
```

Windows-сборка включает серверную службу: перед `npm run dist` на Windows выполните `npm run build:sea --workspace server` и `npm run stage:windows-server --workspace client`. Готовые файлы появятся в `client/dist/`.
> При `npm install` бинарник Electron скачивается с GitHub Releases — машине сборки нужен доступ к `github.com`. За прокси задайте `NODE_EXTRA_CA_CERTS=/path/to/ca.crt` или `ELECTRON_MIRROR`.

## Возможности

**Сотрудник (роль `employee`)**
- Вход под своей учётной записью
- Поиск по подключениям: название, адрес, описание, теги; фильтры по типу (RDP/AnyDesk/RustDesk), категории и тегу; счётчики
- Запуск подключения в один клик («Подключить →»)
- **RDP открывается прямо в окне приложения** — встроенная сессия на canvas (IronRDP WASM + WebSocket-шлюз на сервере), как в Remote Desktop Manager: клавиатура, мышь, колёсико, буфер обмена; отдельное окно mstsc не нужно. В карточке можно указать домен; явные имена `DOMAIN\user` и `user@domain` остаются без изменений. Пароль можно ввести при подключении или сохранить в карточке при защищённом соединении с сервером.
- Чтение документации (Markdown) с поиском и разделами
- Смена собственного пароля

**Администратор (роль `admin`)** — всё перечисленное, плюс:
- Добавление / редактирование / удаление подключений (тип, адрес, порт, категория, теги, логин, описание)
- Создание и редактирование документов (Markdown)
- Управление учётными записями: создание админов и сотрудников, отключение, сброс пароля, удаление (менять и удалять собственную запись нельзя — защита от потери доступа)

## Как выполняется подключение

**RDP** (основной сценарий) — встроенная сессия в окне приложения:

1. Нажмите «Подключить →» на RDP-карточке → откроется полноэкранный режим с запросом пароля. Логин и домен подставляются из карточки; пароль можно ввести вручную или сохранить на сервере.
2. Клиент (IronRDP WASM) туннелирует RDP через сервер по WebSocket `ws://<сервер>/ws/rdp` (протокол RDCleanPath) — **сервер должен иметь сетевой доступ к RDP-узлу**. Поддерживаются CredSSP/NLA; рисуется рабочий стол, работают клавиатура/мышь/колёсико и буфер обмена (текст).
3. Экспериментальный обмен файлами в Electron: скопируйте файлы или папки и вставьте их на другой стороне через Ctrl+V или контекстное меню. В клиенте Windows удалённые файлы предоставляются как виртуальные файлы OLE и загружаются при вставке, без предварительного скачивания. RDP-сессия и приложение должны оставаться открыты до окончания копирования. Если Windows-компонент недоступен, а также на других ОС, используется прежний режим с предварительным скачиванием во временный каталог и кнопками передачи; такие временные файлы требуют ручной очистки. Действуют ограничения протокола и ОС; поддержка зависит от политики RDP-сервера. Проверка реальной вставки в Проводнике с Windows RDP-сервером ещё необходима. В браузерном режиме потоковое сохранение недоступно.
4. Кнопка «Во внешнем клиенте» в той же панели запускает системный клиент (`mstsc` / `xfreerdp` / `remmina`), если встроенный по каким-то причинам не подходит.

Шлюз на сервере принимает только подключения из базы: destination из RDCleanPath-запроса сверяется с RDP-записями (host:port, порт по умолчанию 3389); JWT обязателен. Пароли через шлюз не проходят и не логируются.

| Тип | Основной способ | Внешний клиент |
|-----|-----------------|----------------|
| RDP | **встроенное окно** (IronRDP WASM → `/ws/rdp`) | Windows: `mstsc.exe /v:<адрес>[:port] [/u:user]`; Linux: `xfreerdp3` → `xfreerdp` → `remmina` |
| AnyDesk | `"AnyDesk.exe" <id>` (Windows), `anydesk <id>` (Linux), иначе `anydesk:<id>` | — |
| RustDesk | Экспериментальное встроенное окно в десктоп-клиенте: прямой WebSocket к собственному серверу | — |

Пароли от самих подключений в базе не хранятся (только при необходимости логин) — для встроенного RDP пароль вводится в форме подключения и используется только для этой сессии.

## REST API (кратко)

Все маршруты, кроме `/api/login` и `/api/health`, требуют `Authorization: Bearer <token>`. Запись — только администраторам.

```
POST /api/login                  вход, выдаёт токен (12 ч) и профиль
GET  /api/me                     текущий пользователь
POST /api/change-password        смена своего пароля
GET  /api/stats                  счётчики (для панели)

GET    /api/users                список учётных записей            (admin)
POST   /api/users                создать учётную запись            (admin)
PUT    /api/users/:id            изменить ФИО / роль / отключение  (admin)
POST   /api/users/:id/reset-password  сброс пароля                 (admin)
DELETE /api/users/:id            удалить (не себя)                 (admin)

GET    /api/connections?search=&type=&category=&tag=   список + фильтры
GET    /api/connections/meta     категории, теги, счётчики по типам
POST   /api/connections          создать                             (admin)
PUT    /api/connections/:id      изменить                            (admin)
DELETE /api/connections/:id      удалить                             (admin)

GET    /api/documents?search=&category=   список + разделы
GET    /api/documents/:id                 документ целиком
POST   /api/documents                     создать                    (admin)
PUT    /api/documents/:id                 изменить                   (admin)
DELETE /api/documents/:id                 удалить                    (admin)
```

## Переменные окружения сервера

| Переменная | По умолчанию | Назначение |
|------------|--------------|------------|
| `RDP_MANAGER_PORT` | `8720` | Порт HTTP/HTTPS |
| `RDP_MANAGER_HOST` | `0.0.0.0` | Адрес привязки |
| `RDP_MANAGER_DATA` | `server/data` | Каталог БД и ключа токенов |
| `RDP_MANAGER_LOG_DIR` | выключено | Каталог `server.log` с ротацией; в Windows-службе задан в `%ProgramData%\RDP Manager Server\logs` |
| `RDP_MANAGER_SECRET` | генерируется в `data/secret.key` | Секрет подписи токенов |
| `RDP_MANAGER_TLS_CERT`, `RDP_MANAGER_TLS_KEY` | не заданы | Пути к PEM-сертификату и закрытому ключу для прямого HTTPS/WSS; задаются вместе |
| `RDP_MANAGER_ADMIN_PASSWORD` | `admin123` | Пароль admin при **первом** запуске |
| `RDP_MANAGER_TOKEN_TTL` | `43200` (12 ч) | Время жизни токена, сек |

## Безопасность

- Пароли **пользователей RDP Manager** хешируются **scrypt** (N=16384) с индивидуальной солью, сравнение через `timingSafeEqual`
- Сохранённые пароли подключений (пока только RDP в интерфейсе) шифруются AES-256-GCM отдельным ключом `data/connection-secrets.key`; ключ и БД должны быть защищены правами ОС. Все активные сотрудники после смены своего первоначального пароля могут получить пароль любого подключения; разграничения по карточкам нет. Не сохраняйте пароли, которые нельзя разделять со всеми сотрудниками. При изменении адреса, типа, логина или домена карточки прежний пароль удаляется; для нового назначения задайте его снова.
- Операции с паролями подключений допускаются только по прямому HTTPS или напрямую через loopback. Обычный HTTP по сети и HTTP через reverse proxy запрещены даже с `X-Forwarded-Proto`. Для HTTPS задайте оба пути `RDP_MANAGER_TLS_CERT` и `RDP_MANAGER_TLS_KEY` в среде службы, перезапустите её и укажите клиенту `https://имя-сервера:8720`; сертификату должен доверять каждый клиент. Не отключайте проверку сертификата. Существующие установки по умолчанию используют HTTP и должны быть настроены перед сохранением паролей.
- Токены — HMAC-SHA256 JWT, секрет хранится в `data/secret.key` (chmod 600) и переживает перезапуск
- RDP-шлюз (`/ws/rdp`): только с валидным JWT; цель из RDCleanPath-запроса обязана совпадать с RDP-подключением из БД (host:port) — открытым релеем шлюз не является; CredSSP/NLA выполняет сам WASM-клиент, пароль RDP через шлюз не логируется
- Новые учётные записи и сброшенные пароли требуют смены при первом входе
- Администратор не может отключить, понизить или удалить **себя**
- Рендерер клиента: `contextIsolation`, без `nodeIntegration`, CSP, весь пользовательский HTML экранируется

## Резервное копирование

База — один файл SQLite (`server/data/rdp-manager.db`, WAL-режим). Достаточно регулярно копировать каталог `server/data/` при остановленном сервере, например:

```bash
# Windows (служба RDPManagerServer; данные `%ProgramData%\RDP Manager Server\data`)
xcopy "%ProgramData%\RDP Manager Server\data" D:\backup\rdp-manager /E /Y

# Linux (cron)
0 2 * * *  systemctl stop rdp-manager && cp -a /opt/RDP_manager/server/data /backup/ && systemctl start rdp-manager
```

Более аккуратно — онлайн-бэкап без остановки: `sqlite3 server/data/rdp-manager.db ".backup backup.db"`. Для восстановления сохранённых паролей обязательно сохраните также `data/connection-secrets.key`; утрата или замена ключа сделает пароли недоступными. Защищайте ключ и резервные копии правами ОС и не храните их в репозитории.

## Обслуживание

- **Сменить пароль admin:** веб-панель → «Сброс пароля», или в клиенте → Пользователи.
- **Забыть пароль admin полностью:** остановить сервер, удалить `rdp-manager.db` из каталога `RDP_MANAGER_DATA` (в Windows-службе — `%ProgramData%\RDP Manager Server\data`) — при следующем запуске создастся новая БД (все данные будут потеряны!) с admin/admin123. Поэтому регулярно делайте бэкап.
- **Обновление приложения:** `git pull && npm install && npm run server`.

## Статус реализации / ограничения

- Проверено end-to-end: API (авторизация, CRUD подключений/документов/пользователей, поиск, фильтры), запуск сервера, веб-панель и веб-режим клиента — `http://<IP>:8720/app/`. Смоук-тесты сервера зелёные (`npm test`).
- **Встроенная RDP-сессия**: протокол IronRDP (WASM) покрывает RDP 5–8 + CredSSP/NLA; экзотические конфигурации (RD Gateway, RemoteFX, smartcard) не гарантируются — в этом случае используйте «Во внешнем клиенте». Графическая часть встроенной сессии проверяется только на реальной машине с RDP-узлом; логика шлюза покрыта unit-тестами (`server/test/rdp-gateway.test.js`).
- Графический интерфейс клиента реализован на Electron; бинарник Electron намеренно не входит в репозиторий (ставится через `npm install`).
- Клиент автоматически проверяет и загружает обновления из GitHub Releases; ручная проверка — в разделе «Профиль». GUI сервера проверяет релизы при запуске, раз в 6 часов и по кнопке «Проверить обновления»; для установки серверной версии откройте релиз и запустите единый установщик, выбрав серверный компонент. В приватном репозитории API/автообновление не скачает релиз анонимно — см. `CONTRIBUTING.md`.
- AnyDesk запускается как внешняя программа. RustDesk в десктоп-клиенте экспериментально встроен: его реальная совместимость и безопасность ещё не проверены; системная вставка файлов, серверы `MUST_LOGIN` и браузерный режим не поддерживаются. Прямой `ws://` не защищает метаданные соединения TLS; подробности — `docs/rustdesk-integration.md`.
- Личные данные встроенных RDP и RustDesk можно сохранять локально на Windows отдельно для пользователя RDP Manager и карточки; общие пароли карточек могут храниться на сервере отдельно.
- RDP-шлюз работает через **сервер**, а не напрямую с клиентского ПК: сервер должен маршрутизировать RDP (TCP 3389/3390…) к целевым узлам. Если сервер такой доступ не имеет, используйте внешний клиент.

Если встроенное веб-приложение показывает пустой экран, откройте тот же адрес в обычном браузере на этом компьютере и проверьте сертификат и загрузку страницы. Статус встроенного окна может показать ошибку HTTP, сертификата, ресурса или скрипта; такие сообщения не гарантируют, что найдена единственная причина. Проверка TLS включена по умолчанию; исключение возможно только после ручного подтверждения. Текст ошибок скриптов и адреса ресурсов не сохраняются.

При последующих обновлениях Windows-сервера новая версия установщика останавливает службу RDPManagerServer, но сохраняет её регистрацию и повторно использует её, если путь службы совпадает с ожидаемым. При отключении серверного компонента установщик удаляет только проверенную службу. Установщики старых версий могут по-прежнему помечать службу для удаления. Если служба принадлежит другой программе или не останавливается, установка прерывается; проверьте её в консоли служб. Если служба помечена для удаления, закройте консоль служб и повторите установку. При неудачном обновлении проверьте состояние службы и наличие резервной копии базы и ключа. Обновление работающей службы необходимо дополнительно проверить на реальном Windows.

Для обновления Windows-установки на весь компьютер необходимы права администратора: подтвердите запрос UAC. Если установщик не открылся, загрузите его со страницы релиза и запустите вручную. После подтверждения установки клиент ожидает ответа Windows на запуск установщика; если запуск отклонён или произошла ошибка, клиент остаётся открытым. Обновление со старых версий, где запуск установщика не работает, может потребовать ручного запуска нового установщика. Поведение UAC и обновление требуют проверки на реальном Windows-клиенте.

### Личные данные RDP и RustDesk на Windows

В формах встроенных RDP и RustDesk включён флажок «Сохранить мои данные на этом компьютере». После успешного подключения сохраняются логин, домен и пароль RDP либо пароль устройства RustDesk; коды двухфакторной проверки не сохраняются. Данные подставляются при следующем открытии той же карточки тем же пользователем на этом компьютере. Их можно удалить кнопкой в форме. На других компьютерах и во внешних клиентах эти данные недоступны; при смене адреса назначения или сервера RustDesk прежние данные автоматически не подставляются. Старые записи при изменении или удалении карточки автоматически не удаляются.

Данные зашифрованы через Electron safeStorage/Windows DPAPI для текущей учётной записи Windows, не отправляются на сервер RDP Manager и не работают без доступного системного шифрования. Разделение пользователей RDP Manager — привязка записей в приложении, **не защита от другого человека или программы с доступом к той же учётной записи Windows**; для такой защиты используйте отдельные учётные записи Windows. Администратор компьютера или вредоносная программа в том же профиле могут получить доступ к секретам. Личные данные не отменяют существующий общий пароль карточки: при отсутствии личного значения может использоваться общий пароль. Реальная проверка Windows, RDP и RustDesk необходима.

### SSH и SFTP в десктоп-клиенте

В карточке выберите SSH (терминал) или SFTP (просмотр каталогов и загрузка/скачивание отдельных файлов), укажите адрес, порт, пользователя и при необходимости сохранённый пароль. Клиент соединяется с узлом напрямую, PuTTY и WinSCP не нужны. Перед отправкой пароля нужно **каждый раз** сверить SHA256-отпечаток ключа SSH-сервера по независимому доверенному каналу и подтвердить совпадение. Не подтверждайте неизвестный или изменившийся ключ. Поддерживается вход по паролю; ключи пользователя, интерактивные дополнительные факторы и передача каталогов пока не поддерживаются. Для доступа к сохранённым паролям настройте HTTPS сервера, как описано выше.

В SSH выделение мышью копирует текст; правая кнопка мыши, Ctrl+V, Shift+Insert и кнопка «Вставить» вставляют текст. Ctrl+Shift+C / Ctrl+Insert копируют выделение, Ctrl+C остаётся прерыванием команды. Многострочная вставка требует подтверждения, максимальный размер одной вставки — 60 000 байт UTF-8. Вставка файлов в терминал не поддерживается; для файлов используйте SFTP. Обычные клавиши терминала обрабатывает xterm.js; полная совместимость с настройками и функциями PuTTY не гарантируется.

SFTP показывает два каталога: локальный слева и удалённый справа. Переходите по папкам двойным щелчком, указывайте путь в строке или используйте кнопки «↑» и «Обновить». Выберите обычный файл и нажмите «Отправить» или «Получить»; при совпадении имён требуется подтверждение перезаписи. Передаются только отдельные файлы, папки и символические ссылки не копируются. Правой кнопкой мыши в панели можно обновить каталог, скопировать путь, создать пустой файл или папку, либо передать выбранный файл; в удалённой панели также можно создать символическую ссылку («Ярлык») на абсолютный или относительный путь. Локальные ярлыки не создаются; в удалённую панель также можно вставить скопированные в системный буфер локальные файлы (до 128 за раз).

Контекстное меню выбранного объекта позволяет открыть, изменить, передать, переименовать, перенести в другой каталог той же панели, удалить или скопировать его имя/путь. Дублирование работает для обычных файлов и удалённых папок (включая вложенные); локальные папки дублировать нельзя; удаляются только файлы, ссылки и пустые каталоги, после подтверждения. Существующие объекты не перезаписываются намеренно; при одновременных изменениях другим процессом проверка назначения и переименование не атомарны.

«Скопировать в буфер обмена» для удалённого файла или папки сначала полностью скачивает временную копию на компьютер, затем помещает её в системный буфер; копия доступна до выхода из программы, удаляется при нормальном завершении и может остаться после сбоя. Прогресс отображается для текущего файла. Символические ссылки и специальные файлы не копируются: при их обнаружении операция завершается с ошибкой. При неудачном дублировании на сервере может остаться частичная копия; временная локальная копия при ошибке удаляется. Ограничения: 100 000 объектов и глубина 128 каталогов; имена должны поддерживаться локальной файловой системой. Права, владельцы и даты копии не сохраняются. SFTP не обеспечивает атомарной защиты от подмены каталогов и ссылок при одновременном изменении на сервере. Рекурсивное удаление и пользовательские команды не поддерживаются.

Кнопка «Свойства» (или F9 / контекстное меню) показывает данные выбранного объекта. Для обычных удалённых файлов и каталогов можно изменять права в восьмеричном виде или флажками, а также числовые UID/GID; доступность зависит от прав и возможностей SFTP-сервера. Локальные свойства и символические ссылки доступны только для просмотра. Имена пользователей/групп и контрольная сумма не определяются. Перед применением проверяются полученные свойства, однако SFTP не обеспечивает атомарной защиты от параллельного изменения.

Редактор SFTP открывается двойным щелчком по обычному файлу, клавишей F4 или через контекстное меню. Он поддерживает только текст UTF-8 размером до 2 МиБ (сохранение BOM и единообразных LF/CRLF); бинарные файлы, ссылки и смешанные окончания строк не редактируются. Перед сохранением проверяется, что файл не изменился, однако SFTP не даёт атомарной проверки на конфликт: параллельная запись после проверки возможна. Файл записывается на месте, чтобы сохранить права и владельца; при обрыве записи он может быть частично повреждён. Для важных конфигураций делайте резервную копию.

Для запуска из исходников дополнительно выполните `npm run build:ssh --workspace client`; сборка установщика делает это автоматически. SFTP-передача и интерфейс требуют проверки на целевых серверах и Windows.

### Веб-приложения в десктоп-клиенте

Создайте карточку типа «Веб-приложение» с полным HTTPS-адресом, именем пользователя и при необходимости сохранённым паролем. Сайт открывается в изолированной временной сессии; cookies и данные не сохраняются после закрытия. При недоверенном сертификате можно отменить переход или, сверив SHA-256-отпечаток по независимому каналу, подтвердить переход для этого адреса и сертификата до закрытия окна. Это риск перехвата паролей и данных: не подтверждайте неизвестный сертификат. После подтверждения сохранённые логин и пароль могут автоматически заполняться на исходном адресе, поэтому особенно важно проверить отпечаток. Доступны только HTTPS-страницы; всплывающие окна, скачивания и запросы разрешений заблокированы.

При первой загрузке клиент пытается **один раз** заполнить одну обычную пустую форму с логином и паролем на исходном HTTPS-origin, если адрес отправки формы имеет тот же origin. Вход автоматически не отправляется. При переходе на другой origin, сложных или динамических формах, SSO и MFA может потребоваться ручной вход; формы внутри iframe автоматически не заполняются. Код доверенного сайта после заполнения может прочитать введённые данные, поэтому сохраняйте пароль только для проверенных приложений. Общие ограничения серверного хранилища паролей указаны выше.
